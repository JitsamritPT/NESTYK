## 1. ข้อสรุปสำหรับโปรเจกต์ตอนนี้

- Source of truth ของรายการ: `docs/new-project/agent/create-room/update_room.md` (09/18) — 6 หมวด
- Migration: `migrations/20260318-amenities-catalog-v2.sql` (remap legacy codes)
- Labels: `packages/i18n/src/amenities-catalog-labels.ts`
- API `listFacilities` คืนเฉพาะ 6 กลุ่มใหม่
- UI: `RoomFacilitiesEditor` — ค้นหา, แท็บ All/Selected, accordion หมวด, การ์ด 2 คอลัมน์, ล้างรายการ, เพิ่มรายการอื่น

ควรปรับการจัดหมวดและการเลือกข้อมูลก่อน ไม่ควรเพิ่มรายการทั้งหมดจากระบบโรงแรมหรือสร้างฟอร์มใหญ่ในครั้งเดียว

- คง facilities เป็นข้อมูลไม่บังคับ และคงการบันทึกร่วมกับห้อง
- ใช้รายการมาตรฐานร่วมกันทุกประเภทอสังหาฯ แต่เรียงรายการแนะนำตามประเภท ไม่ปิดกั้นรายการที่อาจมีจริง
- แยกข้อมูลตัวที่พัก, สิ่งอำนวยความสะดวก, เงื่อนไขการอยู่ และสถานที่ใกล้เคียง
- ระยะแรกเปลี่ยนเฉพาะ presentation: หมวดพับได้ ค้นหา ดูรายการที่เลือก ไอคอนสื่อความหมาย
- การรวมรายการซ้ำ การแยกความหมาย และข้อมูลจำนวน/ค่าใช้จ่าย ต้องทำเป็นงาน migration/API แยกต่างหาก
- ไม่มีเครื่องหมายเลือก หมายถึง “ยังไม่ระบุว่ามี” ไม่ใช่ยืนยันว่า “ไม่มี”

## 3. ขอบเขตข้อมูล: อะไรควรอยู่ที่ไหน

| หน้า/หมวด | ข้อมูล | ไม่ควรปน |
| --- | --- | --- |
| รายละเอียดห้อง/บ้าน | จำนวนห้องนอน/น้ำ, พื้นที่, ชั้น, อาคาร, รูปแบบยูนิต, สภาพเฟอร์นิเจอร์ | อุปกรณ์เป็นรายชิ้น |
| สิ่งอำนวยความสะดวก | อุปกรณ์ พื้นที่ใช้งาน ส่วนกลาง ความปลอดภัย บริการ | ค่าเช่าและข้อห้าม |
| เงื่อนไขการอยู่อาศัย — ข้อเสนอใหม่ | สัตว์เลี้ยง สูบบุหรี่ จำนวนผู้พัก ข้อจำกัด | อย่าอ้างว่าระบบรองรับ structured fields แล้ว |
| ค่าเช่าและเงื่อนไข | ราคา/ระยะสัญญา/มัดจำ/ล่วงหน้า และค่าบริการเมื่อพัฒนาเพิ่ม | ไม่กรอกเงินก้อนเดียวกันซ้ำหลายหน้า |
| ทำเลและสถานที่ใกล้เคียง | สถานี โรงพยาบาล โรงเรียน ร้านค้า ระยะทาง | ส่วนกลางของโครงการ |
| รายละเอียดเพิ่มเติม | วิว ทิศ จุดเด่น คำบรรยาย | ข้อมูลสำคัญที่ควรมี field เฉพาะ |

ดูเพล็กซ์/เพนท์เฮาส์เป็นรูปแบบยูนิต ไม่ใช่จำนวนห้องนอน การปรับโครงสร้าง room type เป็นงานแยก ไม่รวมใน UI amenities ระยะแรก

## 4. ชุดรายการที่เสนอ

สัญลักษณ์ลำดับงาน:

- **คงเดิม**: มี code ใน seed ปัจจุบัน ใช้ข้อมูลเดิมได้ แต่บางรายการต้องรอยืนยันความหมาย
- **เพิ่มรอบถัดไป**: เหมาะกับตลาดเช่าห้อง/บ้าน ควรเพิ่มหลังจัดการ mapping เดิม
- **ขยายภายหลัง**: ใช้เฉพาะบางทรัพย์หรือจำเป็นต้องมี structured detail

รายการในส่วนนี้เป็นขอบเขตแค็ตตาล็อกเป้าหมาย ไม่ใช่ข้อเสนอให้แสดงทุกข้อพร้อมกัน

### 4.1 ภายในที่พัก

| กลุ่มย่อย | คงเดิม | เพิ่มรอบถัดไป | ขยายภายหลัง |
| --- | --- | --- | --- |
| เฟอร์นิเจอร์ | ตู้เสื้อผ้า, โต๊ะทำงาน | เตียงและที่นอน, โซฟา, โต๊ะรับประทานอาหาร, ผ้าม่าน/มู่ลี่ | Walk-in closet, โต๊ะเครื่องแป้ง, ตู้เก็บของ, ม่านทึบแสง |
| เครื่องใช้ไฟฟ้า | เครื่องปรับอากาศ, สมาร์ททีวี, ตู้เย็น, ไมโครเวฟ, เครื่องซักผ้า | เครื่องทำน้ำอุ่น, พัดลม, เตาไฟฟ้า/แม่เหล็กไฟฟ้า, เครื่องดูดควัน | ทีวีทั่วไป, เตาแก๊ส, เตาอบ, เครื่องอบผ้า, เครื่องซักอบ, เครื่องล้างจาน, เครื่องกรองน้ำ, เครื่องฟอกอากาศ |
| ครัวและห้องน้ำ | ครัว/พื้นที่ทำอาหาร, ห้องอาบน้ำแยก | อ่างอาบน้ำ | ครัวเปิด/ปิด/ครัวไทย, เคาน์เตอร์และตู้ครัว, ห้องน้ำในห้องนอน |

ข้อกำหนด:

- ไม่เปลี่ยน “ห้องอาบน้ำแยก” เป็น “แยกเปียก–แห้ง” อัตโนมัติจนกว่าจะตกลงนิยาม เพราะไม่รับประกันว่าเป็นข้อมูลเดียวกัน
- Smart TV กับ TV และเครื่องซักอบกับเครื่องซักผ้า ต้องกำหนดความสัมพันธ์ก่อนสร้าง filter หลีกเลี่ยงข้อมูลขัดแย้ง
- สภาพเฟอร์นิเจอร์ ไม่มี/บางส่วน/ครบ เป็น field แยก ไม่อนุมานว่าครบจากจำนวนอุปกรณ์ที่เลือก
- จำนวนเครื่องปรับอากาศเป็นข้อมูลขยาย ไม่ยัดจำนวนลงชื่อ master

### 4.2 พื้นที่ส่วนตัว

- คงเดิม: ระเบียงห้อง/บ้าน, สระว่ายน้ำส่วนตัว
- เพิ่มรอบถัดไป: สวนส่วนตัว, พื้นที่ตากผ้า, เฉลียง/ชาน, ห้องเก็บของ
- ขยายภายหลัง: ดาดฟ้าใช้งานได้, ลานกลางแจ้ง, พื้นที่บาร์บีคิว, จากุซซีส่วนตัว, ทางเข้าแยก, รั้ว, ประตูรั้วอัตโนมัติ, ห้องซักรีด, ห้องแม่บ้าน/ห้องน้ำแม่บ้าน

หากจำนวนห้องเก็บของ/แม่บ้านถูกเก็บในรายละเอียดที่พักภายหลัง ให้แสดงจากแหล่งข้อมูลนั้น ไม่สร้าง checkbox อีกชุดที่ขัดกันได้

### 4.3 ที่จอดรถและ EV

- คงเดิม: ที่จอดรถ — ปัจจุบันมี pop_04 และ srv_04 ต้องจัดการความซ้ำ
- เพิ่มรอบถัดไป: ที่จอดรถจักรยานยนต์, ที่จอดจักรยาน, ที่จอดรถผู้มาติดต่อ
- ขยายภายหลัง: จุดชาร์จ EV ส่วนกลาง, เครื่องชาร์จ EV ส่วนตัว

รายละเอียดที่ต้องเพิ่ม schema ก่อนใช้งาน: จำนวนคัน, ช่องประจำ/ไม่ประจำ/ไม่ทราบ, ในร่ม/กลางแจ้ง/ผสม/ไม่ทราบ, รวมค่าเช่า/จ่ายเพิ่ม/ต้องสอบถาม

ห้ามอนุมานว่า “โครงการมีที่จอดรถ” เท่ากับ “ห้องนี้มีสิทธิ์จอดฟรี 1 คัน”

### 4.4 ส่วนกลางของอาคาร/โครงการ

- คงเดิม: ฟิตเนส, ซาวน่า, ลิฟต์, พื้นที่ทำงานส่วนกลาง, สวนส่วนกลาง, สระว่ายน้ำส่วนกลาง
- เพิ่มรอบถัดไป: ห้องประชุม, ห้องนั่งเล่นส่วนกลาง, สนามเด็กเล่น, ห้องรับพัสดุ, เครื่องซักผ้าส่วนกลาง
- ขยายภายหลัง: สระเด็ก, ห้องโยคะ, สนามกีฬา, ลู่วิ่ง, สวนดาดฟ้า, คลับเฮาส์, ห้องอ่านหนังสือ, ห้องเด็กเล่น, ห้องอบไอน้ำ, จากุซซีส่วนกลาง, ล็อกเกอร์พัสดุ, พื้นที่สัตว์เลี้ยง, จุดล้างตัวสัตว์เลี้ยง, รถรับส่งโครงการ

pop_01 “สระว่ายน้ำ” เดิมไม่ได้ระบุส่วนตัว/ส่วนกลาง จึงต้องเก็บเป็น “สระว่ายน้ำ — ยังไม่ระบุประเภท” จนกว่าผู้ใช้จะยืนยัน

### 4.5 ความปลอดภัย

- คงเดิม: รปภ. 24 ชั่วโมง, คีย์การ์ด/ดิจิตอลดอร์ล็อก, CCTV, เครื่องตรวจจับควันและไฟไหม้, ถังดับเพลิง, ตู้นิรภัย
- เพิ่มรอบถัดไป: แยก Digital door lock ของยูนิต ออกจากระบบคีย์การ์ดอาคาร สำหรับข้อมูลใหม่
- ขยายภายหลัง: ควบคุมการเข้าถึงชั้น, วิดีโออินเตอร์คอม, สัญญาณกันขโมย, เครื่องตรวจจับก๊าซ, ระบบดับเพลิงอัตโนมัติ

ระบุตำแหน่ง/ขอบเขตภายในยูนิตหรือส่วนกลางเมื่อจำเป็น ไม่เปลี่ยน CCTV เดิมให้หมายถึงพื้นที่ส่วนกลางโดยอัตโนมัติ และไม่แนะนำกล้องภายในพื้นที่ส่วนตัวเป็นจุดขายทั่วไป

### 4.6 อินเทอร์เน็ตและบริการ

- คงเดิม: บริการเรียกแม่บ้านทำความสะอาด, นิติบุคคล 24 ชั่วโมง
- เพิ่มรอบถัดไป: อินเทอร์เน็ตพร้อมใช้งาน, Wi-Fi ภายในที่พัก, รองรับติดตั้งอินเทอร์เน็ต, Wi-Fi ส่วนกลาง
- ขยายภายหลัง: บริการซักรีด, เปลี่ยนผ้าปู, เจ้าหน้าที่ต้อนรับ, บริการรับพัสดุ, ดูแลสวน, ดูแลสระว่ายน้ำ

“นิติบุคคล 24 ชั่วโมง” ไม่เท่ากับ รปภ. 24 ชั่วโมง ห้ามใช้แทนกัน และไม่เปลี่ยนเป็นนิติบุคคลทั่วไปจนสูญเสียความหมายเดิม

เมื่อเพิ่มข้อมูลรายห้อง: ระบุค่าใช้จ่ายเป็น รวมค่าเช่า/จ่ายเพิ่ม/ต้องสอบถาม และระบุความถี่/รายละเอียดได้ ค่า is_extra_charge=false เดิมไม่ใช่หลักฐานว่ารวมค่าเช่า

### 4.7 การเข้าถึง

ชุดขยายภายหลัง: ทางเข้าไม่มีขั้น, ทางลาด, ลิฟต์ถึงชั้นที่พัก, ห้องนอนชั้นล่าง, ห้องน้ำชั้นล่าง, ราวจับห้องน้ำ, พื้นที่อาบน้ำไม่มีขอบกั้น, ที่จอดรถสำหรับผู้ใช้รถเข็น

ใช้รายละเอียดที่ยืนยันได้ ไม่ใช้คำรับรองกว้าง ๆ เช่น “รองรับผู้ใช้รถเข็นทุกกรณี” จากการเลือกลิฟต์เพียงข้อเดียว

ระยะแรกแสดง pop_05 ในหมวด display “เงื่อนไขที่พัก” ภายในหน้าเดิมได้ โดยยังส่ง storage key เดิมและไม่สร้างสถานะใหม่ที่ backend ยังเก็บไม่ได้

### 4.9 จุดเด่น และข้อมูลที่ไม่ควรเพิ่มตอนนี้

จุดเด่นเสริม: ห้องมุม, วิวเมือง/สวน/สระ/แม่น้ำ/ทะเล/ภูเขา, ทิศ, ความสูงเพดาน, ปีปรับปรุง ให้เริ่มจากรายละเอียดเพิ่มเติมก่อนหากยังไม่มี schema

ยังไม่ควรนำรายการแนวโรงแรม เช่น อาหารเช้า บาร์ มินิบาร์ เครื่องใช้ห้องน้ำฟรี เสื้อคลุม รองเท้าแตะ บริการนวด เข้ามาเป็นตัวเลือกหลัก แม้มี translation เดิมอยู่ ใช้ custom กับกรณีพิเศษก่อน

## 7. สเปก UI ที่เหมาะกับแอปตอนนี้

1. Header ใช้รูปแบบหน้าย่อยเดิม: back + “สิ่งอำนวยความสะดวก” ไม่มี logo/role ซ้ำ
2. ข้อความสั้น: “เลือกสิ่งที่มีให้ในที่พักนี้ · ไม่บังคับ”
3. ช่องค้นหา ค้นจากชื่อที่แปลแล้วและคำพ้องที่กำหนด ไม่ค้นเฉพาะ code
4. แท็บ “ทั้งหมด” และ “เลือกแล้ว (N)” โดย N นับรายการไม่ซ้ำ รวม custom ตามกติกาที่ระบุชัด
5. หมวดพับได้ พร้อม “เลือกแล้ว N รายการ” แทน 0/10 ซึ่งอาจดูเหมือนต้องกรอกให้ครบ
6. ภายในหมวดใช้ 2 คอลัมน์เฉพาะข้อความสั้น; ข้อความยาวและรายละเอียดค่าใช้จ่ายใช้แถวเต็มความกว้าง
7. รายการมีไอคอน outline ที่สื่อความหมาย 20–24 pt และข้อความเสมอ; selected ใช้พื้นเหลืองอ่อน ขอบเหลือง และ check ไม่พึ่งสีอย่างเดียว
8. พื้นที่กดขั้นต่ำ 44 pt และเป้าหมาย 48–56 pt; รองรับขนาดตัวอักษรระบบและภาษาไทยหลายบรรทัด ไม่ตัดข้อความสำคัญ
9. ตัด “เลือกทั้งหมด” ออกจากการเลือกปกติ; ในแท็บเลือกแล้วมีนำออกทีละรายการ และล้างพร้อมยืนยันหรือ Undo
10. “เพิ่มรายการอื่น” เปิดช่องเพิ่มทีละรายการพร้อมตัวนับความยาว แปลงกลับ customFacilities[] ตาม API เดิม
11. Footer อยู่เหนือ safe area/keyboard ไม่บังรายการท้ายสุด: จำนวนเลือก, ข้อความยังไม่บันทึกห้อง, ปุ่ม “เสร็จแล้ว”
12. ปุ่มเสร็จแล้วใช้ยืนยัน draft กลับหน้าหมวด ไม่สื่อว่า persist แล้ว; back ต้องมีพฤติกรรมสอดคล้องกับ section อื่น

สถานะที่ต้องออกแบบ: กำลังโหลด, โหลดล้มเหลว+ลองใหม่, ค้นหาไม่พบ, ยังไม่เลือก, มี legacy, custom เกินกำหนด, เปลี่ยนใจยกเลิก, keyboard เปิด, ตัวอักษรขนาดใหญ่

สีและฟอนต์ต้องอ้าง tokens ของ @nestyk/ui/native ไม่ hardcode ชุดใหม่จากภาพ mockup ตรวจ contrast ของข้อความเหลืองบนขาวก่อนใช้; ตัวอักษรหลักคงสีเข้ม

## 8. แผนพัฒนาแบบไม่เสี่ยงข้อมูลเดิม

### P0 — UI บน API เดิม

- สร้าง display configuration แยกจาก storage key
- ค้นหา accordion selected view ไอคอน และ custom editor
- ไม่เปลี่ยนความหมาย legacy ไม่เพิ่มจำนวน/ราคาใน UI ที่ยังบันทึกไม่ได้
- หากจะรวม parking เป็นแถวเดียว ต้องมี adapter ที่อ่านได้ทั้งสอง key รักษาตัวที่มีอยู่เมื่อไม่แก้ และนำออกได้ทั้งสองเมื่อผู้ใช้เอาออก; หาก adapter ยังไม่พร้อม ห้ามซ่อน key จนแก้ไม่ได้
- “ยอดนิยม” เป็น shortcut อ้างรายการจริง ไม่เป็นข้อมูลซ้ำ; อาจงดในระยะแรกเพื่อลดความซับซ้อน
- ยังคงข้อมูล optional ไม่เพิ่มเงื่อนไขบังคับเผยแพร่จาก amenities

### P1 — ปรับ catalog และเพิ่มรายการจำเป็น

- สำรวจ master/room links จริงทุก environment ก่อน migration และบันทึก count ก่อน–หลัง
- เพิ่มรายการลำดับ “เพิ่มรอบถัดไป” พร้อม labels th/en/ja/zh, order และ icon mapping
- วาง canonical identity/alias สำหรับรายการซ้ำที่ยืนยันแล้ว; parking ต้องตรวจนิยามก่อนรวม
- ทำ transactional, repeatable migration พร้อม rollback plan และ snapshot mapping
- ไม่เปลี่ยน group ของ master โดยละเลย room_facilities.group_id และ client เก่าที่ส่ง groupCode
- คง compatibility ของ API/read เก่า หรือวาง deployment order ชัดเจน; ไม่ลบ master ที่ห้องเดิมยังอ้างอิง
- สระไม่ระบุประเภทและคีย์การ์ด/ดิจิตอลล็อกแบบรวมต้องขอผู้ใช้ยืนยัน ไม่แตกค่าจากการเดา

### P2 — ข้อมูลละเอียดรายห้อง

ข้อเสนอ schema เชิงแนวคิด ยังไม่ใช่ชื่อ field ที่มีอยู่:

- ขยาย room-facility detail: quantity, scope, chargeMode, note ตาม capability ของแต่ละ amenity
- scope: private/shared/unspecified; chargeMode: included/extra/unknown
- policy แยกจาก facility เช่น pets.status + ข้อจำกัด ไม่ใช้ checkbox เพื่อแทน 4 สถานะ
- applicability เป็นข้อมูลการแนะนำ ไม่ใช่สิทธิ์เลือก
- แยก cost รายห้องออกจาก master.is_extra_charge; migrate true เป็น extra ได้เฉพาะความหมายที่ยืนยันแล้ว ส่วน false เริ่ม unknown ไม่ใช่ included
- ไม่ย้าย custom text ไปเป็นข้อมูลโครงสร้างอัตโนมัติโดยไม่มีการยืนยัน
- ฝั่ง API ต้อง validate จำนวนเป็นค่าที่เหมาะสมกับรายการ, enum, ความยาวข้อความ และ field ที่อนุญาต ไม่รับ detail แบบไร้ schema

รายการขยายภายหลังค่อยเพิ่มตามการใช้งานจริง ไม่จำเป็นต้องสร้างทุก field ใน P2 ครั้งแรก
